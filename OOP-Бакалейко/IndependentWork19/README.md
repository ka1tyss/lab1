Самостійна робота No19

• Тема: Дизайн винятків і політики retry: теорія та кейси Polly.
• Обсяг: 80 хв (2 академічні години)

Мета

Опрацювати теорію обробки винятків у .NET (механізм try-catch-finally, власні типи винятків, коли
кидати виняток i коли повертати Result), вивчити патерни відмовостійкості (Retry, Circuit Breaker,
Bulkhead) та бібліотеку Polly, реалізувати практичні сценарії i підготувати звіт.

## 1. Реалізація власного винятку (`InsufficientFundsException`)
Для банківської предметної області створено спеціалізований виняток `InsufficientFundsException`, успадкований від базового класу `Exception`. Окрім трьох стандартних конструкторів (за замовчуванням, із повідомленням та з внутрішнім винятком `innerException`), клас інкапсулює контекстні властивості тільки для читання: `RequestedAmount` (запитана сума) та `CurrentBalance` (поточний баланс). Це дозволяє блоку `catch` не просто фіксувати факт помилки, а й програмно обробляти фінансові параметри відмови.


## 2. Аналіз реалізованих сценаріїв відмовостійкості (Polly v8)

### Сценарій 1: Виклик зовнішнього платіжного API (`Retry` + `Timeout`)
- **Опис проблеми:** Зовнішні HTTP-сервіси схильні до короткочасних мережевих збоїв (HTTP 503) або «зависання» відповіді при пікових навантаженнях.
- **Обґрунтування стратегії:** Використано комбінацію `Retry` (із експоненційною затримкою `Exponential Backoff`) та внутрішнього `Timeout` (500 мс). Таймаут не дає потоку нескінченно чекати на «завислий» сокет, перетворюючи затримку на `TimeoutRejectedException`, а політика повторів робить ще кілька спроб зі збільшенням паузи, щоб не створювати DDoS-ефект на сервер.
- **Опис виводу:** Перша спроба завершується помилкою мережі, друга переривається за таймаутом через 500 мс, а третя успішно отримує JSON-відповідь.

### Сценарій 2: Доступ до бази даних (`Circuit Breaker`)
- **Опис проблеми:** Якщо пул з'єднань бази даних вичерпано або сервер БД впав, постійні повторні запити лише погіршують ситуацію і блокують ресурси самого застосунку.
- **Обґрунтування стратегії:** Обрано патерн `Circuit Breaker` («Автоматичний вимикач»). Після 3 невдалих запитів підряд ланцюг переходить у стан `Open` і миттєво відхиляє наступні запити винятком `BrokenCircuitException` без реального звернення до БД. Через 2 секунди ланцюг переходить у `Half-Open`, пропускає тестовий запит і після його успіху повертається в нормальний режим `Closed`.
- **Опис виводу:** Запити №1–3 падають із помилкою пулу, запит №4 блокується миттєво самим Polly, а після паузи запити №5–6 успішно виконуються.

### Сценарій 3: Відправлення повідомлень у перевантажену чергу (`Fallback` + `Retry`)
- **Опис проблеми:** Брокер повідомлень (наприклад, RabbitMQ) може тимчасово відхиляти нові події через переповнення черги, але система не повинна втрачати важливі бізнес-події.
- **Обґрунтування стратегії:** Поєднано `Retry` (2 швидкі спроби) та `Fallback` (резервний сценарій). Якщо черга залишається недоступною, `Fallback` перехоплює виняток і зберігає повідомлення у локальне сховище (патерн Outbox) для пізнішої синхронізації.


## 3. Коли кидати виняток, а коли повертати `Result<T>`

Винятки (`throw new ...`) доцільно використовувати для **непередбачуваних, виняткових технічних збоїв або порушення контрактів**, які унеможливлюють нормальне продовження роботи методу (обрив мережі, відсутність файлу конфігурації, передача `null` замість обов'язкового аргументу). Оскільки створення винятку та розкручування стеку викликів (stack trace) є ресурсоємною операцією, їх не варто використовувати для керування штатним потоком виконання програми. Натомість патерн **`Result<T>`** (повернення об'єкта-обгортки зі статусом успіху, значенням або описом бізнес-помилки) є оптимальним для **очікуваних валідаційних та доменних сценаріїв** — наприклад, невдалого входу користувача, відсутності товару на складі або некоректно заповненої форми, де помилка є штатним варіантом розвитку подій.

---

## 4. Загальні висновки
Бібліотека **Polly** (особливо сучасний API `ResiliencePipelineBuilder`) дозволяє декларативно відокремити бізнес-логіку від інфраструктурного коду обробки збоїв, роблячи застосунки стійкими до тимчасових деградацій мережі та зовнішніх сервісів. Головними перевагами є гнучка композиція стратегій (`Retry`, `Timeout`, `Circuit Breaker`, `Fallback`) та вбудоване логування подій. Водночас обмеженням і ризиком є неправильне налаштування параметрів: надмірна кількість повторів без експоненційної затримки може спричинити каскадний збій (лавиноподібне навантаження), а застосування `Retry` до неідемпотентних операцій (наприклад, списання коштів без ключа ідемпотентності) здатне призвести до дублювання транзакцій.
